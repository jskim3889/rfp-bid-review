1. 과업 고르기 (7강 #76~79)

제안 업무 전체가 아니라 "공고를 받고 참여 여부와 작성 일정을 정하는 첫 검토" 한 과업만 떼어 냈다. 제안서 본문 작성과 가격 산정은 범위에서 뺐다.

기준 (#77)이 과업
빈도와 소요 시간건당 2~3시간, 월 6건 이상 → 한 달에 12~18시간 이상. #77의 기준(주 1회 이상, 회당 30분 이상)을 넘는다
입력이 디지털 텍스트인가대부분 HWP·PDF. HWP는 스킬 폴더의 추출 스크립트로, 스캔 PDF는 쪽 이미지로 읽는다
기준이 문서화되어 있는가공고의 평가 배점표가 곧 기준이다. 회사 쪽 기준(실적·자격)은 프로필 파일로 정리했다. 무엇을 먼저 보는지(가중치)는 아직 머릿속에 있다
결과를 검증하기 쉬운가모든 판정에 공고 조항을 근거로 달게 해서, 원문을 펴 보면 바로 확인된다
틀렸을 때의 비용큼. 마감 일시나 참가 자격을 잘못 읽으면 입찰 기회를 잃는다 → 사람이 최종 결정하고, 확인하지 못한 자격은 "판단불가"로 남긴다
데이터 민감도공고는 공개 문서다. 회사의 실적·계약 정보는 내부 정보다

가치 높음 · 위험 있음 7강 #78의 "설계해서 진행" 칸이다. 그래서 사람이 최종 결정하는 단계, 근거 표시, 판단불가 분리를 절차에 넣었다.

스킬을 고른 이유 쓰는 사람이 나와 회사 동료다. 내 PC에 있는 HWP 공고와 회사 내부 실적 파일을 읽어야 한다. 웹앱으로 만들면 회사 정보를 서버에 올려야 하고 비밀·접근 통제 책임이 생긴다(#79).

무엇을 하는지와 언제 꺼내는지를 한 문장에 함께 썼다. 사람들이 실제로 쓰는 말("이 공고 들어갈 만한가")을 발동 조건으로 넣었다.

  4. 종합 의견: 참여 / 조건부 / 비권고와 이유 3줄. 최종 결정은 사람이 한다
  5. 마감 시각부터 거꾸로 작성 일정을 세운다. 주말·공휴일은 빼고, 여유가 없으면 "일정 촉박" 경고를 단다
  6. 날짜·금액·배점을 원문과 다시 대조한다. 발주처 담당자의 이름과 연락처는 옮기지 않는다

# 제안요청서 유불리 분석과 작성 스케줄

## 입력
- 필수: 입찰공고문, 제안요청서 (PDF·HWP·HWPX·DOCX). 대화에 첨부하거나 작업 폴더의 `input/<공고번호>/`에 넣는다
- 선택: 과업지시서, 제안서 평가기준표, 변경공고, 질의응답
- 자사 정보: 같은 폴더의 `company-profile.md`. [확인 필요] 칸은 판단불가로 처리한다. 이 파일은 외부에 올리지 않는다
- HWP·HWPX는 `python scripts/hwp_text.py <파일>`로 텍스트를 뽑는다. 스캔 PDF는 쪽 이미지로 읽고, 그렇게 읽은 값은 원문 대조 대상으로 표시한다
- 기준일: 따로 말이 없으면 오늘. 지난 공고를 다시 검토할 때는 공고일을 기준일로 두고 남은 작업일을 그날부터 센다

## 절차
1. 문서 목록을 먼저 확인한다. 변경공고가 있으면 최신 공고를 기준으로 하고, 원공고와 달라진 항목을 따로 적는다. 표지의 "(안)", 앞부분의 메모, 이미 채워진 별지처럼 작업본으로 보이는 흔적이 있으면 "게시본과 대조 필요"로 표시한다.
2. 요건을 뽑는다. 항목마다 근거를 [문서명 p.쪽] 형태로 단다. 문서에 없으면 "명시 없음"이라고 쓰고 추정하지 않는다.
   - 사업 개요 / 일정 / 참가 자격 / 평가 / 과업 범위
3. 자사와 대조해 유불리를 판정한다. 판정은 유리 / 보통 / 불리 / 판단불가 넷 중 하나로 하고, 근거를 한 줄씩 단다.
   - 결격 사유는 표 맨 위에 따로 표시한다
   - 정량 평가: 구간표대로 자사 점수를 계산하고, 확인 여부에 따라 달라지면 "3~7점"처럼 범위로 쓴다
   - 서로 어긋나는 조항은 질의 사항으로 옮긴다
   - 정성 평가: 과업 범위와 자사 보유 기술의 겹침, 유사 사업 경험
   - 경쟁 환경: 근거가 없으면 판단불가로 둔다
   - 판단 기준 가중치 [확인 필요]
4. 종합 의견: 참여 권고 / 조건부 권고 / 비권고 중 하나와 이유 3줄. 최종 결정은 사람이 한다고 표시한다.
5. 작성 스케줄: 제출 마감 시각에서 거꾸로 계산한다.
   - 착수 → 질의 → 목차 → 초안 → 내부 검토 → 수정 → 증빙 → 편집·업로드 → 제출 → 발표 준비
   - 단위별 기본 소요일 [확인 필요]
   - 주말과 공휴일은 빼고, 남은 작업일이 모자라면 "일정 촉박" 경고
   - 공고가 정한 날짜는 고정 일정으로 표시한다
6. 검증한다. 날짜, 시각, 금액, 배점은 원문과 다시 대조한다. 발주처 담당자의 이름과 연락처는 보고서에 옮기지 않는다.

## 출력 양식
외부 파일을 부르지 않는 HTML 브리핑 보고서 한 장. 결론부터 쓴다.
1. 한눈에 보기 2. 결론과 이유 3줄 3. 결격 사유 점검 4. 유불리 분석표
5. 작성 스케줄 6. 요건 추출표(부록) 7. 사람이 확인할 것 8. 입력 문서·AI 초안 고지

## 하지 않는 것
- 문서에 없는 요건을 짐작해 채우지 않는다
- 입찰 가격을 산정하지 않는다
- 참여 여부를 확정하지 않는다
- 자사 정보와 공고를 이 작업 밖으로 보내지 않는다

절차 2·3·5의 세부 항목 일부를 줄여 실었다. 스킬 폴더 구성: SKILL.md, company-profile.md(제출하지 않음), scripts/hwp_text.py(HWP 텍스트 추출).

4. 스킬 전후 비교

구분스킬 전 (손으로)스킬 후
소요 시간공고 1건에 2~3시간생성 약 3분(HWP 추출 포함). 결과 검토에 드는 사람 시간은 아직 재지 못했다
결과물요건표와 일정표를 직접 작성결론부터 쓴 HTML 브리핑 1장. 결격 점검, 유불리 13항목, 작성 일정, 요건표, 질의 사항이 들어간다
근거요건을 항목으로 정리하지만 공고의 어느 조항인지는 적지 않는다모든 판정에 공고 조항을 단다. 근거가 없으면 "판단불가"
배점 계산배점표를 읽고 유불리를 대략 판단한다정량 배점 구간표로 자사 점수를 계산하고, 미확인 값에 따라 범위(3~7점)로 보여 준다
일정마감에서 거꾸로 표로 짠다같은 방식(마감 역산 표)을 자동으로 하고, 주말과 "마감 전일 18:00" 같은 고정 일정을 따로 표시한다. 차이가 가장 작은 항목이다

스킬 전의 시간·빈도·작업 방식은 담당자가 답한 평소 방식이다. 스킬 후의 시간은 실행 로그의 시작·종료 시각으로 쟀다. 가장 큰 차이는 시간보다 근거 표시와 배점 계산이다. 평소에는 조항 위치를 적지 않고 배점을 대략 판단했기 때문에, 결론이 맞는지 다른 사람이 다시 확인하기 어려웠다.

5. "이것을 해도 되는가?"

애매한 점판단과 극복 수단남은 위험
회사의 실적·계약 정보를 외부 AI 서비스에 넣어도 되나판단에 필요한 항목만 추린 프로필 파일 하나로 한정했다. 원문 대조를 거친 값만 쓰고 출처를 달았다. 이 파일, 입력 공고, 결과물은 GitHub에 올리지 않게 막았다(.gitignore). 이 제출 페이지에는 프로필 원문을 싣지 않았다AI 서비스로 전송되는 것 자체는 피할 수 없다. 회사 차원에서 쓸 수 있는 AI 도구와 데이터 처리 조건을 정해야 한다
공고문에 발주처 담당자의 이름·전화번호가 있다보고서에 옮기지 않는 규칙을 절차 6에 넣었다. 생성된 브리핑에서 이름·번호를 검색해 0건임을 확인했다입력 원본에는 남아 있으므로 원본 보관 폴더도 공유하지 않는다
AI의 판정을 그대로 입찰 결정에 써도 되나최종 결정은 사람이 한다는 고지와 "AI 작성 초안" 표시를 고정했다. 확인하지 못한 자격은 유리·불리로 짐작하지 않고 "판단불가"로 분리했다"조건부 참여"라는 결론만 읽고 조건을 건너뛸 수 있다
제안서에 허위 기재가 생길 위험이 공고는 허위 기재 시 평가 제외와 손해배상을 경고한다. 스킬은 제안서 문구를 쓰지 않고, 실적 인정 여부처럼 불확실한 값은 질의 사항으로 넘긴다뒤 단계(제안서 작성)에서 AI를 쓰면 같은 위험이 다시 생긴다

6. 신뢰성: 결과가 맞는지 어떻게 확인했나

  • 원문 대조: 금액, 계약기간, 제출·개찰 일시, 협상적격 점수, 업종코드, 선금 비율, 지체상금, 쪽수 제한 등 19개 값을 공고문·제안요청서 텍스트와 대조했다. 정성·정량 배점표 전 행도 대조했다. 모두 일치했다.
  • 실제 결과와 비교: 회사는 이 사업에 참여해 수주했고 지금 수행 중이다. 스킬의 "참여 권고" 방향과 같다.
틀렸거나 약했던 점
  • 블라인드 시험이 아니었다. 스킬에 넣은 회사 프로필의 "수행 중 과업" 목록에 이 사업이 이미 들어 있었다. 결론이 실제와 맞았다는 것만으로 판단력을 증명하지는 못한다. 다음 시험은 프로필에 없는 새 공고로 한다.
  • 첫 실행에서 출력 양식이 요구한 부록(요건 추출표)이 빠졌다. 양식과 대조하다 발견해 보완했다.
  • 입력한 제안요청서가 게시본이 아니라 회사 작업본이었다. 회의 메모와 회사 정보가 섞여 있었다. 이를 계기로 "작업본 흔적을 찾아 게시본과 대조하라"는 규칙을 추가했다.
  • 작성 일정의 단계별 소요일은 기본값이다. 회사의 실제 소요일과 판단 가중치는 아직 반영하지 않았다.

7. 실제 업무에 쓰려면 더 필요한 것

  • 단계별 실제 소요일과 판단 가중치를 담당자에게 받아 SKILL.md의 [확인 필요] 두 곳을 채운다
  • 프로필에 없는 새 공고 2~3건으로 블라인드 시험을 하고, 사람 검토 시간을 함께 잰다
  • 소기업 확인서, 신용평가등급, 업종 등록처럼 매번 확인하는 회사 서류를 프로필에 유효기간과 함께 넣는다
  • 회사가 승인한 AI 도구 안에서만 쓰도록 사용 범위를 정한다
